# Greptile

A closed-source AI pull-request reviewer that indexes each repository into a code graph plus a pgvector embedding store, then runs a multi-hop agent over the diff — and, with TREX, actually executes the branch in a sandbox to prove a bug before commenting.

## 1. Verdict

**A component, not a platform competitor — but the single best-executed PR-review product examined, and the one whose mechanisms Specera should steal most directly.** Greptile stays inside one SDLC stage (PR review, plus an adjacent testing capability) and does not attempt requirements, architecture, release, or incidents. The single thing it does better than anything else is **verification by execution**: TREX runs the PR branch in a rootless podman sandbox, mocks API calls, clicks through the UI, writes and runs tests, and attaches logs, screenshots, API traces or a video to the review comment — turning "I think this is a bug" into "here is the failing run" (https://www.greptile.com/blog/trex, 2026-06-15). Second best: its Jira integration extracts issue keys **deterministically** from PR title, description, and branch name, then reviews the change against the ticket's acceptance criteria and flags "where the change doesn't do what was asked" (https://www.greptile.com/docs/jira-integration.md) — which is exactly the requirement↔code link Specera needs, done without an LLM guess. What limits it: it is a review tool with a ~32-person team, it reaches no other SDLC stage, and its documented graph is a single-repo graph extended only by cloning up to 20 GB of sibling repos read-only.

## 2. Core architecture and unique mechanism

No source access. All below from Greptile's own docs and engineering blog, fetched 2026-08-04.

**The stack is documented in unusual detail because it ships self-hosted.** `FACT` https://www.greptile.com/docs/system-architecture.md names the actual services and ports: Web UI (3000), "REST API, business logic" (3001), auth (3002), a webhook service that "Receives GitHub/GitLab webhooks" (3007), SAML for enterprise SSO (5225). Background workers: one "Splits repositories into chunks for indexing", one "Generates repository summaries", one "Generates PR reviews using LLMs", plus scheduled "analytics, cleanup". An LLM proxy "Routes requests to configured LLM providers". Orchestration is **Hatchet** ("Workflow orchestration API" + execution engine) over a Redis "Message queue for Hatchet" — corroborated by Hatchet's own customer page (https://hatchet.run/customers/greptile). Storage is **PostgreSQL with pgvector**, holding "Repository metadata and summaries", "Code embeddings", and "Review history and analytics".

`INFERENCE` So the retrieval substrate is **hybrid and, critically, in one database**: the graph and the vectors both live in Postgres. There is no Neo4j, no dedicated vector DB, no separate graph engine named anywhere. That is a deliberate simplicity choice that makes the whole product deployable as `docker compose up` on one Linux VM — and it is why Greptile can offer air-gapped self-host when Augment cannot.

**Graph construction.** `FACT` https://www.greptile.com/docs/how-greptile-works/graph-based-codebase-context.md describes three steps: (1) scanning — "Parses every file to extract directories, files, functions, classes, variables"; (2) relationship mapping — "Connects all elements: function calls, imports, dependencies, variable usage"; (3) storage — "Stores the complete graph for instant querying during code reviews". Node types: files, directories, functions, classes, variables, parameters, external calls, imports. `FACT` The doc **does not name tree-sitter, a parser, or any language grammar**, and does not state incremental-update semantics or per-language coverage. `UNVERIFIED` Secondary sources assert tree-sitter; no Greptile page fetched says so. To verify: a Greptile engineering post naming the parser, or the self-hosted image's dependency manifest.

**Embedding strategy — the one place Greptile published real numbers.** `FACT` https://www.greptile.com/blog/semantic-codebase-search (2025-04-15) reports two measured findings: (a) "Semantic search on codebases works better if you first translate the code to natural language, before generating embedding vectors" — query-to-code cosine similarity 0.7280 vs query-to-**description** 0.8152, a 12% gain; (b) "it also works better if you chunk more 'tightly' - on a per-function level rather than a per-file level" — full file 0.718032, full file with the function 0.739421, just the function 0.768347. `INFERENCE` Combined with the "Generates repository summaries" worker in the architecture doc, this means Greptile embeds **LLM-written natural-language descriptions of code, not code**. That is a concrete, reproducible retrieval design decision with published evidence behind it — more than Augment or Graphify offer.

**Query path.** `VENDOR CLAIM` v4 (2026-03-05) uses multi-hop investigation — tracing dependencies, checking git history, following leads across files in a reasoning loop rather than a single pass over the diff — and the homepage says Greptile "deploys parallel agents". `UNVERIFIED` Third-party sources say v4 is built on the Anthropic Claude Agent SDK; no Greptile page fetched confirms this. To verify: a first-party changelog or the self-hosted image's dependencies.

**Cross-repo.** `FACT` "Repo Clusters" group related repositories "so that whenever Greptile reviews a PR in one of them, it automatically reads the others as read-only context"; Greptile "clones the other members read-only". Limits: "up to 20 GB of repositories by total size", minimum 2 repos. Clusters are auto-suggested "based on shared contributors, meaning repositories the same people have committed to over the last 90 days"; `context.repos` in `greptile.json` overrides (https://www.greptile.com/docs/code-review/cross-repo-context.md). `INFERENCE` This is **repo-adjacency, not a cross-repo graph**: sibling repos are cloned and made available as context, not linked by resolved edges. A service-to-service call across two repos is not a graph edge in Greptile.

**TREX — execution as evidence.** `FACT` https://www.greptile.com/blog/trex (2026-06-15, Daksh Gupta): "TREX (short for Test, Run, Execute)"; the reviewer "picks out the behavior worth running and spins up a TREX agent. The agent spins up a sandbox, runs the relevant code, and reports back on issues." Evidence attached to the comment: "logs, screenshots, API traces, execution scripts, or even a video of a UI change playing out." `VENDOR CLAIM` "Greptile review with TREX catches 20% more bugs" in Greptile's evals; the founder adds that "most of the new bugs caught could not have been caught with more inference, they required code execution" (https://x.com/dakshgup/status/2066536928716235254). `FACT` Sandbox is a "locked-down rootless podman container so that we have kernel guarantees that it sees only things it's supposed to", using chmod permission bits, mount-namespace masking, and chroot root isolation (https://www.greptile.com/blog/sandboxing-agents-at-the-kernel-level, 2025-09-29).

**Feedback loop.** `FACT` https://www.greptile.com/docs/how-greptile-works/memory-and-learning.md: learns from three signals — team comments on PRs, replies to Greptile, and thumbs-up/down reactions — and tracks counters of the form `semicolonComments {made: 10, addressed: 0, reactions: -3}`, suppressing a style comment class "after 3 ignores". `VENDOR CLAIM` "80% reduction in ignored comments, 3x higher suggestion adoption rate", personalisation emerging in 8–12 weeks. `INFERENCE` This is the most concrete published mechanism for the hardest problem in AI review — comment fatigue — and it is a simple counter per comment-category, not a fine-tune.

## 3. Strongest capabilities

- `FACT` **Execution-backed review (TREX).** Runs the branch, mocks inputs, exercises UI, writes and runs unit tests, attaches a video/logs/traces as proof. No other product in this file set executes the code under review. https://www.greptile.com/blog/trex
- `FACT` **Deterministic ticket linkage.** Jira integration "picks up issue keys and links from the PR title, description, and branch name", can "search Jira for related work while reviewing", uses "the ticket's description and acceptance criteria" as review context, and can "point out where the change doesn't do what was asked". Strictly read-only: "Greptile never writes to Jira." A Linear integration exists as a separate doc page. https://www.greptile.com/docs/jira-integration.md, https://www.greptile.com/docs/linear-integration.md
- `FACT` **Real air-gapped self-host, licensed.** "Use Self-Hosted if you need data sovereignty, air-gapped environments, or custom LLM providers." Docker Compose (up to 100 developers, single Linux VM, AWS Terraform provisioning available) or Kubernetes (100+ developers, horizontal scaling, HA). Bring-your-own LLM across OpenAI, Anthropic, AWS Bedrock, Azure OpenAI, GCP Vertex AI; three model roles required (smart for review, fast for summarisation, embeddings for indexing). SCM: GitHub, GitLab, **Perforce**. https://www.greptile.com/docs/deployment-options.md
- `FACT` **Published retrieval experiment with numbers** (NL-description embeddings beat code embeddings 0.8152 vs 0.7280; function-level chunks beat file-level 0.768 vs 0.718). https://www.greptile.com/blog/semantic-codebase-search
- `FACT` **A/B-measured model upgrade.** v4 vs v3 across "hundreds of thousands of PRs": addressed comments per PR 0.92 → 1.60 (+74%), comment-addressing rate 30% → 43%, positive developer replies 0.31 → 0.52 (+68%), upvote reactions 0.05 → 0.08 (+60%). https://www.greptile.com/blog/greptile-v4 (2026-03-05). **Self-reported**, but the metric chosen — *addressed* comments, not comments emitted — is the honest one.
- `FACT` **Nitpick suppression as a documented subsystem**, with per-category counters and a 3-ignore threshold, plus a "Controlling Nitpickiness" config doc. https://www.greptile.com/docs/how-greptile-works/nitpicks.md, .../code-review/controlling-nitpickiness.md
- `FACT` Distribution and logos: "9,000+ teams"; Substack, Klaviyo, Retool, Nvidia, Brex, Scale, PostHog, Mintlify, Zapier, Joby, WorkOS, Compass, Bilt, Crossmint, Browserbase, Material Security (https://www.greptile.com/, fetched 2026-08-04). Named testimonial from James Reggio, CTO @ Brex.
- `FACT` Full language support listed: Python, JavaScript, TypeScript, Go, Elixir, Java, C, C++, C#, Swift, PHP, Rust (homepage).

## 4. Critical weaknesses

- `FACT` **Single-stage product.** The entire documentation index (https://www.greptile.com/docs/llms.txt, 47 pages) is code review, MCP, deployment, security, and integrations. There is **no page for release, deployment gating, monitoring, incidents, PRD/requirements authoring, ADRs, or threat modelling**. Greptile does not compete for Specera's platform position — it competes for one row of it.
- `INFERENCE` **The "graph" is shallower than the marketing implies.** The graph doc names nodes and edge kinds but no parser, no language grammar list, no resolution strategy for dynamic dispatch/DI/reflection, and no incremental-update semantics. Basis: the full text of https://www.greptile.com/docs/how-greptile-works/graph-based-codebase-context.md. `INFERENCE` Given that the storage is Postgres+pgvector and the published retrieval research is entirely about embeddings, the embedding index is likely doing most of the retrieval work and the graph is an adjacency aid — the inverse of how it is marketed.
- `FACT` **Cross-repo is clone-and-read, capped at 20 GB per cluster, minimum 2 repos**, with clusters inferred from *shared contributors in the last 90 days* rather than from actual code dependencies. `INFERENCE` For a 200-microservice estate this both misses real dependencies (services with disjoint contributor sets) and blows the size cap.
- `FACT` **No first-party no-training commitment found.** https://www.greptile.com/security covers SOC 2 Type II, retention, deletion, and subprocessors, but a "we do not train on your code" statement was not present in what was fetched, and no such wording surfaced in search. `INFERENCE` Given inference runs through OpenAI and Anthropic APIs, the relevant guarantee is those providers' zero-retention terms, not Greptile's. Contrast Augment, which states "We never train on our customer's proprietary data" on its security page. To verify: request the DPA from security@greptile.com.
- `FACT` **Cloud tier stores your code.** "code is stored on encrypted AWS filesystems and cached until GitHub/GitLab access revocation" (https://www.greptile.com/security). `INFERENCE` This is a persistent copy of the customer's source in Greptile's AWS account, not an ephemeral clone — a material procurement fact and the reason enterprises will be pushed to the licensed self-host tier.
- `FACT` **The 82% figure is Greptile's own, and its methodology excludes false positives by construction.** It is published first-party at https://www.greptile.com/benchmarks (HTTP 200, coordinator-verified 2026-08-04): "82%… catch rate, 41% higher than Bugbot (58%)", over 50 bug-fix PRs from Sentry, Cal.com, Grafana, Keycloak, and Discourse. The disqualifying admission is verbatim on the same page: *"false positives, style suggestions, and unrelated comments did not affect the catch rate."* Vendor-run, vendor-chosen dataset, conducted July 2025 — predating v3 and v4. It measures recall only and must never be quoted as accuracy.
- `FACT` **An independent benchmark exists and puts Greptile far lower.** `withmartian/code-review-benchmark` (https://github.com/withmartian/code-review-benchmark) is MIT-licensed, 224 stars, last pushed 2026-07-13, with results under three judge models; it computes **precision and recall** against human-curated golden comments. Its README states the motivation: "Without shared evals for these tools, every company grades its own homework." Micro-averaged from its raw `evaluations.json` (judge `claude-opus-4-5`): **greptile-v4 ≈ 33.1% precision / 56.9% recall (78 tp, 158 fp, 59 fn)**; greptile-v4-1 ≈ 40.5% / 48.2%. For context in the same file: cubic-v2 56.3% precision, augment 47.5%, bugbot 47.2%, copilot 28.3%, coderabbit 25.7%. `UNVERIFIED` caveats that must travel with these numbers: the micro-average was computed by this spike, not published by Martian, whose leaderboard may macro-average or use a different judge; and this corpus shares its five repos with Greptile's own benchmark, so the two are related, not independent samples. Full working: [`.spike/evidence-greptile.md`](../../../../.spike/evidence-greptile.md) (not a deliverable).
- `FACT` **Greptile has never published a false-positive rate**, despite "far lower false positive rate" being the v4 headline claim (https://www.greptile.com/blog/greptile-v4). Every published metric is an engagement proxy — upvote ratio, action rate, addressed rate. Their own v4 figure "% of comments addressed = 43%" implies 57% of comments are not acted on. `INFERENCE` This is the category's defining measurement failure, not Greptile's alone, and it is developed as a cross-cutting finding in [`../../comparison.md`](../../comparison.md) §3.
- `UNVERIFIED` A separate third-party claim of "11 false positives to CodeRabbit's 2" over 50 PRs circulates in competitor-authored (macroscope.com) and affiliate content (dev.to, aicoolies). Unmethodological and commercially motivated — do not cite. The Martian figures above supersede it.
- `FACT` **Self-host requires a paid licence and is Enterprise-only** ("Self-hosted requires a license", deployment-options doc; "Option to self-host in your own infrastructure" under Enterprise/custom pricing). **No public price for self-host found.**
- `INFERENCE` **Small team, single product.** `UNVERIFIED` aggregator data puts headcount at ~32 (Tracxn, as of 2026-06-30) and funding at a $4.1M seed (Initialized/YC, June 2024) plus a $25M Series A led by Benchmark (September 2025), ~$29.1M total; some outlets round to "$30M". None of this is first-party. `FACT` **No acquisition and no discontinuation found as of 2026-08-04** — the company shipped v4 in March 2026, TREX in June 2026, and a new pricing model in March 2026.
- `INFERENCE` **Prompt-injection surface via TREX is the sharpest risk in this file.** TREX executes attacker-authored branch code and reviews attacker-authored PR text and Jira tickets. The podman/chroot/mount-namespace sandbox (2025-09-29 post) addresses *file* exfiltration by the agent, but no page fetched addresses (a) network egress from the sandbox, (b) a malicious PR description instructing the reviewer, or (c) an open-source drive-by PR triggering execution in a customer's self-hosted environment. To verify: ask for the TREX network policy.

- **Pro**: "$30/seat/month" where a seat is a developer who received a review that billing period; "50 credits included per seat", "$1 per additional credit", "Unlimited Users", custom rules, "Connect unlimited external apps".

`FACT` The v4 post (2026-03-05) states the shift explicitly: "a base + usage model, similar to most other AI coding tools", $30/developer/month with 50 included reviews, then $1 per additional review. `INFERENCE` Same conclusion as Augment: **pure per-seat is dead in this category; the unit is the review.** Note the seat definition is usage-gated (only developers who actually received a review are billed), which is a genuinely buyer-friendly detail worth copying.

## 7. Ideas to adopt or avoid

### Adopt
- **Verification by execution before commenting.** Specera should adopt the TREX pattern for its highest-severity findings: when the reviewer believes a change breaks behaviour, spin a sandbox, reproduce it, and attach the artefact (log, trace, screenshot, video) to the comment. It converts precision from a statistical claim into per-comment evidence, and it is the strongest answer available to "AI review is noisy". Source: https://www.greptile.com/blog/trex.
- **Deterministic issue-key extraction from PR title, description, and branch name.** This is the cheap, exact version of the requirement↔code edge that Graphify leaves to an LLM guess. Specera should extract keys from all three locations, resolve them against the tracker, and treat the resulting edge as `EXTRACTED`, not `INFERRED`. Source: https://www.greptile.com/docs/jira-integration.md.
- **Review the diff against the ticket's acceptance criteria and report the gap.** "Point out where the change doesn't do what was asked" is a distinct, high-value review output that no code-only reviewer can produce — and it is directly on Specera's thesis. Source: same.
- **Read-only by default on the tracker.** "Greptile never writes to Jira" is a trust posture worth copying for v1: earn write access after the read-side output is trusted.
- **Per-category ignore counters with a suppression threshold.** `semicolonComments {made: 10, addressed: 0, reactions: -3}` → suppress after 3 ignores. This is a ~50-line mechanism that solves comment fatigue better than prompt tuning, and it produces an auditable reason for every suppression. Source: https://www.greptile.com/docs/how-greptile-works/memory-and-learning.md.
- **Embed natural-language descriptions of code, chunked per function, not raw code per file.** Published numbers: 0.8152 vs 0.7280 similarity for description-vs-code, 0.768 vs 0.718 for function-vs-file chunking. If Specera ships any embedding tier alongside its graph, start here rather than re-deriving it. Source: https://www.greptile.com/blog/semantic-codebase-search.
- **Measure *addressed* comments, not comments emitted.** Greptile's v4 A/B reports addressed-comments-per-PR and addressing rate, which are the only review metrics that correlate with value. Specera's review eval should use the same denominator. Source: https://www.greptile.com/blog/greptile-v4.
- **Rootless podman + mount-namespace masking + chroot as the agent sandbox baseline**, with the threat model written down (agent coerced into reading secrets and exfiltrating them). Source: https://www.greptile.com/blog/sandboxing-agents-at-the-kernel-level.
- **Usage-gated seat definition**: bill only developers who actually received a review in the period. Removes the shelfware objection from the sales conversation.
- **Single-Postgres deployability.** Graph and vectors in one PostgreSQL+pgvector instance is what makes `docker compose up` self-host viable for ≤100 developers. If Specera wants air-gapped enterprise deals, resisting a five-datastore architecture is a strategic decision, not a shortcut.

### Avoid
- **Inferring repository relationships from shared contributors.** 90-day committer overlap is a proxy for team structure, not for code dependency; it will both over- and under-cluster a microservice estate. Specera should cluster by resolved import/call/API edges.
- **Cross-repo context by cloning up to 20 GB read-only.** It does not scale and produces no edges — the sibling repos are context, not graph.
- **Marketing "code graph" while publishing only embedding research.** If Specera claims a graph, the docs must name the parser, the grammars, the edge kinds, the resolution limits, and the incremental-update semantics. Greptile's graph doc names none of these.
- **Persisting customer source in the vendor's cloud "until access revocation".** Ephemeral clones with explicit TTLs are a better default and a cheaper procurement conversation.
- **Shipping an enterprise security page with no no-training statement.** Absence is read as a "no" by procurement.

## 8. Build, borrow, buy, integrate, or reject

**Borrow.** Greptile is closed and proprietary, so nothing is reusable as code, and it is not a platform to buy or partner with — it occupies one row of Specera's table and would compete for the same PR-review budget. But it is the richest mechanism library in this file set: TREX's verification-by-execution, deterministic Jira-key extraction with acceptance-criteria diffing, per-category nitpick suppression counters, and the description-embedding/function-chunking retrieval results are all directly implementable and all published with either numbers or precise mechanics. `INFERENCE` The competitive read: Greptile will get better at review faster than Specera can, so Specera should not try to out-review it — it should make review one output of a graph that also carries requirements, ADRs, and release state, and should match Greptile on the two procurement facts it gets right (air-gapped self-host, credit-metered pricing) while beating it on the one it gets wrong (no published no-training commitment, customer code persisted in vendor cloud).
