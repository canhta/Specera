# Atlassian Rovo (Rovo Search / Chat / Agents, Rovo Studio, Rovo Dev, Teamwork Graph)

Atlassian's AI layer over the systems of record it owns (Jira, Confluence, Bitbucket, Compass, JSM) plus ~100 third-party connectors, all normalised into the Teamwork Graph — a genuinely typed object/relationship graph — with Rovo Dev extending it into PR review that checks code against Jira acceptance criteria.

*All web evidence fetched 2026-08-04. Live Atlassian Rovo MCP probing performed 2026-08-04 against site `all-it.atlassian.net` (cloudId `64f8159f-9ec4-48da-92e7-03f59979fbe4`) — **strictly read-only**; no object was created, edited, commented on, transitioned, or deleted. Peer file for the GitHub side: [github-copilot.md](./github-copilot.md); for the single-vendor-owns-everything comparison: [gitlab-duo.md](./gitlab-duo.md).*

## 1. Verdict

**Existentially threatening, and on precisely Specera's chosen wedge.** `FACT` Rovo Dev code review already "reviews pull requests in Bitbucket and GitHub… to validate code changes against acceptance criteria in Jira", reading AC from summary, description, and custom fields named `Acceptance Criteria`, `AC`, `ACs`, `Business Requirements`, `Functional Requirements`, `Requirements`, `Definition of Done` or `DoD`, and emitting one of three verdicts per criterion: met, "missing from the code", or "need manual checking" — **generally available**, not beta (https://support.atlassian.com/rovo/docs/check-acceptance-criteria-in-a-code-review/). That is Specera's requirement→code verification loop, shipping, at $20/developer/month, on both major SCMs. The single thing Atlassian does better than anyone: it owns the requirement artifact itself, so its AC checker needs no integration to find the requirement. What kills it: `FACT` (first-hand, MCP) the durable link it builds is a **branch-name string match** and the durable *evidence* is a PR comment — and the Teamwork Graph, which should hold the traceable edges, returned for three real Jira work items in an active software project **only `AtlassianUser` relationships**, not even the epic→child edge that the Jira REST API confirms exists, while warning that relationship types are "TTL-limited… truncated to the retention window of **90 days**". `INFERENCE` (rests on both): Atlassian has the requirement, the checker, and a real graph — and still cannot answer "prove this release satisfied these requirements" twelve months later. Specera's remaining defensible ground is the *artifact*, not the *check*.

## 2. Core architecture and unique mechanism

**Teamwork Graph is a real typed graph, not a search index.** `FACT` "Teamwork Graph doesn't just store individual objects—it maps relationships between them"; every item is an *object* with an *object type* defining "its category and the set of properties it has" (https://developer.atlassian.com/platform/teamwork-graph/what-is-teamwork-graph/). `FACT` (first-hand, MCP tool schema for `getTeamworkGraphContext`) the type system is enumerable and includes DevOps types: `ExternalPullRequest`, `ExternalRepository`, `ExternalDeployment`, `ExternalService`, `ExternalDesign`, `CompassComponent`, `AssetsObject`, `JiraWorkItem`, `JiraSprint`, `JiraVersion`, `ConfluencePage`, `AtlassianGoal`, `FocusFocusArea`, `LoomMeeting`, `ExternalCalendarEvent`, `ExternalConversation`, `ExternalDocument`, `ExternalOrganisation`, `ExternalPosition`. Relationships are *named* (`atlassian_user_created_jira_work_item`, `jira_work_item_links_external_build`) and objects are addressed by ARI (`ari:cloud:jira:<cloudId>:issue/11599`). `INFERENCE`: this settles the open question — the Teamwork Graph is a graph with a schema, not a Lucene index with a graph-shaped marketing name. It is a stronger substrate than anything GitHub or GitLab exposes.

**It is queryable — but not by anyone in production.** `FACT` The Teamwork Graph API supports GraphQL and Cypher: "Execute these Cypher queries via the Teamwork Graph API by wrapping them in a GraphQL `cypherQuery` request." `FACT` "the Teamwork Graph API is still in Early Access (EAP). Timelines for Preview and General Availability (GA) for the Teamwork Graph API are not yet determined", and EAP apps "cannot deploy the app in production environments or on production sites" and "cannot be distribute[d] (via Marketplace or direct distribution links)" (https://developer.atlassian.com/platform/teamwork-graph/querying-ingested-data/). `INFERENCE`: the graph is real, and closed. No third party can build a shipping product on it today.

**Ingestion is connector-shaped, in three fidelity tiers.** `FACT` Connectors "extract data from source systems, map it to Teamwork Graph's object types, and push it into the graph via bulk APIs"; ~100 out-of-the-box connectors (Google Drive, Slack, GitHub, …). Three types: **synced** (Atlassian stores and indexes all workspace content under a service/admin account — "the best quality search"), **direct** (retrieved live via the provider's search API, "not stored or indexed by Atlassian"), and **Smart Link** (per-user, from Smart Link history, no admin setup) (https://support.atlassian.com/organization-administration/docs/teamwork-graph-connector-types/). `INFERENCE`: a direct or Smart Link connector cannot support traceability at all — there is no stored edge to audit, only a live lookup. Only synced connectors put anything durable in the graph, and they require a service account with workspace-wide read.

**The requirement→code link is a branch-name string match.** `FACT` Rovo Dev "identifies the correct work item by checking the branch name for work item keys (e.g. ABC-1234)"; failing that it examines commit messages, and "won't proceed if multiple keys are found there"; the docs advise "link your pull request to one Jira work item by adding its work item key to the branch name" (acceptance-criteria doc). `INFERENCE`: one issue per PR by construction, keyed off a mutable string — architecturally the same primitive as GitHub's closing keyword, with a tighter cardinality limit.

**The durable dev-link substrate that does exist is the Development Information API.** `FACT` `POST /rest/devinfo/0.10/bulk` stores repositories, commits, branches and pull requests, associated to issues via `issueKeys` arrays or `associations` with `issueIdOrKeys`; upsert semantics keyed on `updateSequenceId`; retrieval `GET /rest/devinfo/0.10/repository/{repositoryId}` returns "repository & 400 latest entities"; three DELETE endpoints including `bulkByProperties`; scopes `write:dev-info:jira` / `read:dev-info:jira` / `delete:dev-info:jira`; "These APIs are available to Atlassian Connect apps and on-premise integrations using OAuth"; Connect apps need the `jiraDevelopmentTool` module, Forge apps `devops:developmentInfoProvider` (https://developer.atlassian.com/cloud/jira/software/rest/api-group-development-information/). `INFERENCE`: this — not the Teamwork Graph — is the production-supported, third-party-writable, durable link store in Jira today, and it is the seam Specera should use.

**Agents are Forge modules, and they can be triggered by automation.** `FACT` `rovo:agent` manifest keys: `key`, `name` (≤30 chars), `description`, `icon`, `prompt` ("Custom LLM prompt where you describe how your Agent will behave"), `conversationStarters`, `actions`, `followUpPrompt`; actions are separate `rovo:action` modules backed by Forge functions with plain-text name/description so the agent decides when to invoke them. `FACT` "You can add Agents to Automation rules. This will invoke the Agent to act asynchronously in response to Atlassian app events or schedules" (https://developer.atlassian.com/platform/forge/manifest-reference/modules/rovo-agent/). `VENDOR CLAIM`/`UNVERIFIED`: `rovo:mcp` module, allowing apps to expose actions as tools in Rovo Studio, is in **EAP**; and a `rovo:agent-connector` module is listed as EAP.

## 3. Strongest capabilities

- `FACT` **AC-aware PR review, GA, on GitHub as well as Bitbucket.** Three-state per-criterion verdict against Jira acceptance criteria; enabled in Bitbucket **by default**, with repo-admin permission required to turn it off (https://support.atlassian.com/rovo/docs/check-acceptance-criteria-in-a-code-review/, https://support.atlassian.com/rovo/docs/enable-code-reviews/). No other vendor in this spike reads the requirement text and grades the diff against it.
- `FACT` **A typed, ARI-addressed graph spanning products and third parties**, with named relationship types and cross-product traversal in one call — architecturally ahead of GitHub's and GitLab's flat link models.
- `FACT` **A production, third-party-writable durable link store**: the Development Information API, with upsert-by-`updateSequenceId`, issue-key associations, and explicit OAuth scopes for Connect and on-prem integrations.
- `FACT` **Agents are automation-triggerable**, not just chat — Forge agents run asynchronously off Atlassian events or schedules, so an evidence-producing agent can be event-driven without polling.
- `FACT` **Enterprise data posture is credible.** "The data you submit and the responses you receive from Rovo are not shared with third-party-hosted LLM providers for them to use to train or improve their services"; eligible Cloud Enterprise customers "can elect to use only Atlassian-hosted LLMs, restricting LLM usage to those within the Atlassian Cloud boundary"; "Rovo has completed the external assessment and compliance certifications for SOC 2 and ISO 27001"; HIPAA supported for Chat, Agents and Search in HIPAA-enabled environments; data residency keeps "in-scope app data… in the region you've selected" (https://www.atlassian.com/trust/atlassian-intelligence).
- `FACT` **Overage is currently not billed.** "Atlassian is not currently billing for extra usage above your Rovo credit allowance", with "at least 90 days' notice before credit limits take effect" (https://support.atlassian.com/rovo/docs/rovo-usage-limits/). `INFERENCE`: for now Rovo's marginal cost to a customer is effectively zero, which is a hard price point to compete against.

## 4. Critical weaknesses

- `FACT` (first-hand, MCP, 2026-08-04) **The graph does not contain the edges traceability needs — not even native Jira hierarchy.** `getTeamworkGraphContext` on `JiraWorkItem` FUT-803 (Story, "Ready For QA"), FUT-842 (Task, "In Review") and FUT-792 (**Epic**) each returned *only* `AtlassianUser` relationships: `atlassian_user_created_jira_work_item`, `atlassian_user_assigned_jira_work_item`, `atlassian_user_reported_jira_work_item`, `atlassian_user_updated_jira_work_item`. **No** `ExternalPullRequest`, `ExternalRepository`, `ExternalDeployment`, `ExternalBuild`, `ConfluencePage`, or parent/child edge — despite `searchJiraIssuesUsingJql` on FUT-797 confirming `fields.parent.key = "FUT-792"` on the same site in the same session. `getJiraIssueRemoteIssueLinks(FUT-803)` returned `[]`. `INFERENCE`: for this site the graph is a people-and-activity graph, not a delivery graph. `UNVERIFIED` whether the absence of DevOps edges is because no synced DevOps connector is configured here — that would be verified by an admin view of the org's Teamwork Graph connectors, which read-only MCP access does not expose. The absence of the **Jira-native epic→child edge**, however, is not explicable by a missing connector and is a genuine graph-completeness gap.
- `FACT` (first-hand, MCP) **The graph forgets.** Every traversal returned the warning: *"The following relationships are TTL-limited and were truncated to the retention window of **90 days**: `atlassian_user_created_jira_work_item`, `atlassian_user_updated_jira_work_item`, `jira_work_item_has_changed_jira_priority`, `jira_work_item_has_changed_jira_status`."* `INFERENCE`: a 90-day TTL on status-change and authorship relationships is disqualifying for audit. An auditor asking "who moved this to Done, and when, relative to the release" gets nothing for anything older than a quarter. This is the hardest single finding in this file and it came from the product, not the docs.
- `FACT` **The Teamwork Graph API cannot be used in production or distributed** (EAP; no Preview/GA timeline). `INFERENCE`: Specera cannot build on the one Atlassian asset that would make it defensible, and neither can anyone else — which is also why Atlassian's own graph is under-exploited.
- `FACT` **Rovo Dev's PR↔issue link is a branch-name string, single-issue.** Multiple keys in commit messages cause it to abort. `INFERENCE`: multi-requirement PRs and cross-repo releases — the normal enterprise case — are out of scope.
- `UNVERIFIED` **AC-check output appears to be advisory prose only.** Neither https://support.atlassian.com/rovo/docs/check-acceptance-criteria-in-a-code-review/ nor https://support.atlassian.com/rovo/docs/enable-code-reviews/ states that the result is posted as a build/commit status or that it can block a merge; both describe comments and feedback. Would be verified by a documented commit-status or merge-check integration for Rovo Dev. `INFERENCE` (pending that): the verdict "AC2 is missing from the code" exists as a comment in a PR thread, is not machine-readable, is not retained as a distinct object, and does not gate anything.
- `FACT` **Non-synced connectors store nothing.** Direct connectors' content "is not stored or indexed by Atlassian"; Smart Link connectors derive from individual users' link history. `INFERENCE`: whether a given customer's GitHub data is durably in the graph depends on which connector tier an admin chose — traceability that varies by connector configuration is not traceability.
- `FACT` **Credit economics are per-request and coarse**: Rovo Agents 10 credits/request, Rovo Chat Quick Answer 10, Deep Research **100**, Think Deeper typically 50–100+, Teamwork Graph API 1–10 (https://support.atlassian.com/rovo/docs/rovo-usage-limits/). Against Jira Standard's 25 credits/user/month, a single Deep Research call consumes four users' entire monthly allowance. `INFERENCE`: allowances are sized for occasional chat, not for a per-PR verification agent — and the "not currently billing" grace makes the true steady-state cost unknowable.
- `FACT` **Rovo Dev is a separate paid SKU**: $20 per developer/month, 2,000 Rovo Dev credits, $0.01 per credit overage, and "acceptance criteria checks and custom instructions are only available to users on a Rovo Dev Standard plan", with the further constraint that "the pull request author's Rovo Dev Standard plan must be on the Jira site connected to the Bitbucket workspace or GitHub organization". `INFERENCE`: the check silently does not run for PRs authored by unlicensed contributors — coverage is per-author, not per-repository, which is exactly the wrong shape for a compliance control.
- `FACT` **Bitbucket merge-check enforcement is Premium-gated**: on the free tier unresolved checks warn but do not prevent merging; Premium enables "Users won't be able to merge if their pull request has unresolved merge checks" (https://support.atlassian.com/bitbucket-cloud/docs/suggest-or-require-checks-before-a-merge/).
- `UNVERIFIED` **Rovo Studio's status.** Atlassian community posts describe the unified building experience as "now in open beta" while a company blog describes it as "now generally available" — both dated around TEAM '26. Treat as `VENDOR CLAIM` in either direction; would be verified by a support-docs page carrying an explicit GA label.
- `FACT` **Model routing spans three external vendors.** Atlassian-hosted Llama and Mixtral plus OpenAI GPT, Anthropic Claude and Google Gemini, with "dynamic routing to select the optimal model". `INFERENCE`: the customer cannot know which vendor processed a given AC verdict unless they take the Enterprise Atlassian-hosted-only option — which restricts capability.

## 6. Security, deployment, and license

**License** — Closed commercial SaaS. No source. Extension is via **Forge** (`rovo:agent`, `rovo:action`, `teamwork-graph-connector`, `devops:developmentInfoProvider`, `rovo:mcp` [EAP], `rovo:agent-connector` [EAP]), **Connect** (`jiraDevelopmentTool`), REST APIs with OAuth 2.0 scopes, Jira Automation, webhooks, and the Marketplace.

**Pricing** — `FACT` Rovo credits are included in paid Jira/Confluence/Service Collection/Teamwork Collection subscriptions: Standard **25** credits/user/month (Teamwork Collection 250), Premium **70** (700), Enterprise **150** (1,500); pooled at organisation level; monthly reset, no rollover. Billable at 10 credits/request for Agents and Chat Quick Answer, 100 for Deep Research, 1–10 for Teamwork Graph API; search, summaries, definitions and chart insights are free. Overage **not currently billed**, ≥90 days' notice promised, dashboard visibility "starting in August 2026" (https://support.atlassian.com/rovo/docs/rovo-usage-limits/). `FACT` Rovo Dev is separate: **$20/developer/month**, 2,000 Rovo Dev credits, **$0.01/credit** overage, 30-day trial (https://www.atlassian.com/software/rovo-dev/pricing).

**Training on customer code** — `FACT` "The data you submit and the responses you receive from Rovo are not shared with third-party-hosted LLM providers for them to use to train or improve their services." `FACT` Caveat in the same source: Atlassian may use **de-identified metadata to fine-tune internal open-source models** under stated safeguards. `INFERENCE`: this is a weaker guarantee than GitLab's flat "GitLab does not train generative AI models" and GitHub's stated zero-data-retention agreements — Atlassian reserves a first-party fine-tuning right that the other two do not.

**Model providers** — `FACT` Atlassian-hosted Llama and Mixtral; third-party-hosted OpenAI GPT, Anthropic Claude, Google Gemini; dynamic routing per scenario.

**Data residency** — `FACT` "all of your in-scope app data will remain stored in the region you've selected"; by default data "transfers outside your site to third-party LLM providers for processing", and only **eligible Cloud Enterprise** customers can restrict inference to Atlassian-hosted LLMs inside the Atlassian Cloud boundary. `INFERENCE`: for non-Enterprise customers, requirement text and diff content leave the residency region at inference time — a material objection for regulated buyers, and one Specera can answer with a self-hosted or in-region deployment.

**Compliance** — `FACT` "Rovo has completed the external assessment and compliance certifications for SOC 2 and ISO 27001"; HIPAA support for Chat, Agents and Search in HIPAA-enabled environments; GDPR via the existing DPA. `UNVERIFIED`: FedRAMP status for Rovo specifically.

**Deployment** — Cloud only. `INFERENCE` (rests on Rovo being built on Teamwork Graph, a cloud platform service): there is no self-managed or air-gapped Rovo, unlike GitLab Duo Self-Hosted. For Data Center customers this is a hard exclusion. `UNVERIFIED`: any Rovo capability on Jira/Confluence Data Center.

**Auth / tenancy** — `FACT` Synced connectors index a whole workspace "using a service or admin account". `FACT` Forge app agents access only data "in the workspace that the app is installed in". `FACT` (first-hand, MCP) OAuth scopes are granular and product-split — this session's token carried `read:jira-work`, `write:jira-work` and a separate Confluence scope set including `write:page:confluence` and `write:comment:confluence`.

**Prompt-injection surface** — `INFERENCE` (rests on documented ingestion): Rovo agents reason over Jira descriptions, Confluence pages, Slack messages and connector-ingested third-party documents, and Rovo Dev reads PR diffs and branch names — all attacker-writable in an open Jira Service Management portal or an external-contributor PR. `FACT` Forge actions are arbitrary code the agent chooses to invoke based on a plain-text description. `INFERENCE`: a service-desk ticket body is a viable injection vector into an agent holding a workspace-wide service-account index. `UNVERIFIED`: Atlassian's prompt-injection mitigations for Rovo agents — no doc fetched addressed them.

## 7. Ideas to adopt or avoid

### Adopt

- **Read acceptance criteria from the fields teams actually use.** Rovo Dev's field-name list — `Acceptance Criteria`, `AC`, `ACs`, `Business Requirements`, `Functional Requirements`, `Requirements`, `Definition of Done`, `DoD`, plus summary and description — is empirically derived and costs nothing to copy. Specera should match it exactly on day one, then *improve* on it by assigning each parsed criterion a stable ID and persisting it, which Atlassian does not do.
- **The three-state verdict.** met / missing / **needs manual checking** is the right vocabulary: it refuses to claim verification it cannot perform. Specera should adopt the same trichotomy and make "needs manual checking" a first-class outcome that requires a named human sign-off recorded in the evidence artifact.
- **Write into the Development Information API instead of building a parallel link store.** `POST /rest/devinfo/0.10/bulk` with `issueKeys` associations, upsert on `updateSequenceId`, plus the `devops:developmentInfoProvider` Forge module, gives Specera a supported way to make its evidence appear natively in the Jira development panel — visible to every Jira user, no new UI, no adoption cost.
- **Named relationship types and ARIs.** `atlassian_user_created_jira_work_item` and `ari:cloud:jira:<cloud>:issue/11599` are the right shape for an evidence edge: typed predicate, globally-addressable subject and object. Specera's evidence graph should use the same convention so its records can be joined to Atlassian's without a mapping table.
- **Agent invocation from Automation rules.** Event-driven, asynchronous agent execution off platform events is the correct trigger model for verification runs — no polling, no webhook receiver to operate.
- **Bitbucket/GitHub commit-status as the gate.** Bitbucket merge checks require *n* successful builds via the commit status REST API and, on Premium, block the merge. Specera should post a commit status on both platforms so the same code path produces a real gate on either SCM.

### Avoid

- **A TTL on the evidence.** A 90-day retention window on status-change and authorship relationships makes the graph useless for audit at exactly the moment an audit happens. Specera's evidence records must be append-only and retained for the customer's stated retention period, with the period configurable and the policy itself auditable.
- **Verdicts as prose in a comment thread.** An AC verdict that exists only as PR-comment text cannot be counted, queried, exported, or re-checked. Specera's output must be a structured record per criterion, addressable by ID.
- **One-issue-per-PR keyed off a branch name.** Renaming a branch or opening a PR that satisfies three stories breaks the entire chain. Specera should resolve the link from multiple signals (branch, commit trailers, PR body, explicit API call) and persist the resolved set, not re-derive it.
- **Per-author licensing for a compliance control.** A check that runs only when the PR *author* holds a licence produces silently incomplete coverage. Specera should licence per repository or per organisation so coverage is a property of the project, not of who pushed.
- **Connector tiers that silently change durability.** Direct and Smart Link connectors store nothing; a customer can believe they have traceability and have a live search. If Specera offers ingestion modes, the mode must be visible on every artifact the mode affects.
- **Grading the diff instead of the test run.** Rovo's checker infers whether code appears to satisfy AC. Specera must tie a satisfied criterion to an executed check with a recorded outcome, or it inherits the same unfalsifiable claim.
- **Reserving a fine-tuning right on customer metadata.** "De-identified metadata to fine-tune internal models" is the clause an enterprise security review will stop on. A flat no-training commitment is a cheap differentiator.

## 8. Build, borrow, buy, integrate, or reject

**Integrate — and treat as the more urgent of the two existential threats.** Nothing is borrowable (closed SaaS), but Atlassian's extension surface is the richest in this spike and, unusually, includes a *durable write path*: Forge `rovo:agent` + `rovo:action` for agent behaviour, Jira Automation for event triggering, the Development Information API (`devops:developmentInfoProvider` / `jiraDevelopmentTool`) for persisting requirement→code links inside Jira itself, and Bitbucket/GitHub commit statuses for the gate. `INFERENCE`: the strategic reading is that Atlassian has already taken the *idea* — grading a diff against Jira acceptance criteria, GA on both SCMs, largely free at the margin today — and has left the *artifact* undone: no per-criterion identity, no structured verdict record, an advisory-only output, a 90-day TTL on the graph's own history, and a graph API in EAP that no one may ship on. Specera's honest positioning is therefore **evidence, not detection**: not "we can tell whether AC2 is met", which Atlassian already sells for $20/dev/month, but "we can prove, twelve months later and outside Atlassian's retention window, exactly which check established that AC2 was met, on which commit, in which release." If Specera's plan is the checker rather than the record, this competitor has already shipped it.
