# GitLab Duo (Duo Core / Pro / Enterprise, Duo Agent Platform, foundational flows)

GitLab's AI layer on top of a platform that already owns the whole chain in one Postgres data model: issue → branch → merge request → CI pipeline → security scan report → release object → deployment, with Duo agents and "flows" attached to each stage.

*All web evidence fetched 2026-08-04. No source read — this is a docs-only assessment of a source-available/proprietary-EE product. Peer file for the GitHub side of this comparison: [github-copilot.md](./github-copilot.md); shared background is not repeated here.*

## 1. Verdict

**The most existentially threatening competitor in the spike, and the threat is not the AI.** GitLab already ships, as GA product, most of what Specera proposes to build: a first-class `Requirement` object verified pass/fail by a CI artifact, `report_artifacts` captured into an auditable release evidence JSON, in-toto SLSA provenance on build artifacts, merge-blocking policy-as-code, external status checks that a third party can use to block a merge, and streamed audit events — all inside one product with one identity model and no cross-system synchronisation. The single thing it does better than anything else: `FACT` it is the only vendor here where requirement → code → test → scan → release are rows in the same database rather than links across four SaaS boundaries. What kills it as a *complete* answer: `FACT` the requirements report is a flat map of requirement IID → `"passed"`/`"failed"` (https://docs.gitlab.com/user/project/requirements/) — it records *that* a requirement passed, never *which test, which commit, or which evidence* proved it, and `FACT` GitLab's own AI reviewers are constitutionally non-authoritative ("The flow never sets the **Approve** state, even when it finds no issues" — https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/security_review/). `INFERENCE` (rests on both): GitLab has the *containers* for evidence and refuses to let AI *fill* them. That seam — and only that seam — is where Specera survives.

## 2. Core architecture and unique mechanism

**One data model, not an integration.** `FACT` The traceability primitives are native objects, not references: closing patterns in an MR description close issues and work cross-project, with the documented default regex `\b((?:[Cc]los(?:e[sd]?|ing)|\b[Ff]ix(?:e[sd]|ing)?|\b[Rr]esolv(?:e[sd]?|ing)|\b[Ii]mplement(?:s|ed|ing)?)(:?) +(?:(?:issues? +)?%{issue_ref}…|([A-Z][A-Z0-9_]+-\d+))+)`, and MRs created from an issue **inherit the issue's milestone and labels** (https://docs.gitlab.com/user/project/issues/managing_issues/). `INFERENCE`: contrast with GitHub, where manual issue↔PR linking is capped at ten and same-repo only — GitLab's closing patterns are cross-project by design and the trailing `[A-Z][A-Z0-9_]+-\d+` alternative in the regex is an external-tracker (Jira-style) key, so GitLab parses Jira keys out of MR descriptions natively.

**Requirements as verified objects.** `FACT` "A requirement is an artifact in GitLab which describes the specific behavior of your product." A CI job emits `artifacts: reports: requirements: tmp/requirements.json` (key renamed `requirements_v2` where work items are enabled); the JSON maps requirement IID to `"passed"` or `"failed"`, with `{"*":"passed"}` as a wildcard; states are satisfied / failed / missing; a `CI_HAS_OPEN_REQUIREMENTS` variable gates the job. Ultimate only (https://docs.gitlab.com/user/project/requirements/). `FACT` The same page states requirements and test cases "are being migrated to work items."

**Release evidence.** `FACT` On release creation GitLab automatically snapshots a JSON evidence object containing `release` (id, tag_name, name, project, created_at, description), `milestones`, `packages` (added GitLab 18.11), and `report_artifacts` (job artifacts from the last pipeline), explicitly "to facilitate internal processes, like external audits"; downloadable from the Releases page or via the collect-release-evidence API. Report artifacts in evidence are **Ultimate only** (https://docs.gitlab.com/user/project/releases/release_evidence/).

**Build provenance.** `FACT` Setting `RUNNER_GENERATE_ARTIFACTS_METADATA=true` makes the runner emit `{ARTIFACT_NAME}-metadata.json` in **in-toto v0.1 Statement format carrying a SLSA 1.0 Provenance predicate**, with SHA256 artifact digests, builder identity, timestamps, resolved dependencies, and CI/CD variable *names* with values blanked (https://docs.gitlab.com/ci/runners/configure_runners/#artifact-attestation).

**Duo Agent Platform.** `FACT` "Introduced as a beta in GitLab 18.2", **generally available in GitLab 18.8** (self-managed GA behind flags `agentic_chat_ga` / `ai_duo_agent_platform_ga_rollout_self_managed`, flags removed in 18.10) (https://docs.gitlab.com/user/duo_agent_platform/). Three agent classes: foundational (Planner, Data Analyst, CI Expert [Premium+], Security Analyst [Ultimate]), custom (GA 18.8, UI-configured: display name, visibility, system prompt, tool allow-list), and external. `FACT` "In GitLab 18.9 and earlier, you cannot use the Agent Platform with the GitLab Duo Enterprise add-on" — i.e. the new platform and the old seat SKU were mutually exclusive until 18.10.

**Foundational flows** — `FACT` (https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/), all on Claude Sonnet 4, all three offerings: Software Development; **Developer** ("Create actionable merge requests from issues"); Fix CI/CD Pipeline; Convert to GitLab CI/CD (Jenkins migration); Code Review; Security Review; Agentic SAST Vulnerability Resolution; SAST False Positive Detection; Secret False Positive Detection; Agentic Breaking Change Resolution. Custom flows GA in **GitLab 19.2**.

**External agents.** `FACT` Claude Code, OpenAI Codex, Amazon Q Developer and Google Gemini run *inside* GitLab as external agents (introduced 18.3, renamed from "CLI agents" in 18.6); they read repo context, open ready-to-merge changes, post inline comments, execute CI/CD pipelines, and are wired to triggers on MR events (approved, ready, conflicts), work-item creation and status changes, running under a service account with CI/CD variables for credentials (https://docs.gitlab.com/user/duo_agent_platform/agents/external/).

**The gate.** `FACT` External status checks: "Status checks are API calls to external systems that request the status of an external requirement"; configured per project (name, URL, optional target branch, HMAC shared secret); the external service posts back via the status-checks REST API; **"To block the merging of merge requests when external checks fail"** an admin enables "Status checks must succeed". Ultimate, GA (https://docs.gitlab.com/user/project/merge_requests/status_checks/). `FACT` Merge request approval policies (ex scan result policies) are YAML under `approval_policy:` in a dedicated security-policy project, up to five policies, rule types `scan_finding` / `license_finding` / `any_merge_request`, keys `vulnerability_states` (`newly_detected`, `new_needs_triage`, `new_dismissed`), `approval_settings.prevent_approval_by_author`, `enforcement_type: enforce|warn`, `bypass_settings`; enforced at group/subgroup/project on protected target branches; **bypasses generate audit events** (https://docs.gitlab.com/user/application_security/policies/merge_request_approval_policies/).

## 3. Strongest capabilities

- `FACT` **Issue → MR → tests → scan → release → deploy inside one system with one data model.** No connector, no webhook lag, no ID mapping. Every other competitor in this spike, Specera's own design included, spans at least two vendors.
- `FACT` **Machine-verified requirements already exist** (`artifacts:reports:requirements`, satisfied/failed, Ultimate). This is the closest thing to Specera's proposed wedge shipping in a GA product today.
- `FACT` **Durable, exportable evidence artifacts already exist**: release evidence JSON including `report_artifacts` from the release pipeline, plus SLSA/in-toto build provenance, plus audit event streaming to S3/GCP Logging (https://docs.gitlab.com/user/compliance/).
- `FACT` **Merge gating is genuinely available to third parties.** External status checks with HMAC-signed callbacks can be made merge-blocking. `INFERENCE`: unlike GitHub — where Copilot review's refusal to block leaves the required-check slot empty by omission — GitLab deliberately publishes a blocking API for external systems. Specera can be a first-class merge gate on GitLab without any bypass-actor style compliance regression.
- `FACT` **Self-hosted models incl. air-gapped.** Duo Self-Hosted keeps "all request and response data in your own environment"; offline licence supported for "fully isolated networks"; Code Suggestions / non-agentic Chat / Code Explanation / Test Generation / Refactor / Fix GA since 17.9, Code Review GA since 18.3, Agent Platform GA 18.8 (https://docs.gitlab.com/administration/gitlab_duo_self_hosted/). No other vendor in this set offers an air-gapped path for the full agent platform.
- `FACT` **Training posture is the cleanest wording in the set**: "GitLab does not train generative AI models" and "All GitLab AI model sub-processors are restricted from using model input and output to train models" (https://docs.gitlab.com/user/gitlab_duo/data_usage/).
- `FACT` **Third-party agents are hosted, not merely integrated** — Claude Code, Codex, Amazon Q and Gemini execute against the repo under GitLab service accounts and event triggers.

## 4. Critical weaknesses

- `FACT` **The requirements report carries no evidence, only a verdict.** The artifact is `{"1":"passed","2":"failed"}` keyed by requirement IID. `INFERENCE`: nothing in it identifies the test that ran, the commit under test, the assertion, or the reviewer. A satisfied requirement in GitLab is an unsigned assertion by whatever job wrote the file — any job can write `{"*":"passed"}` and mark **every open requirement** satisfied in one line. That is the exact failure mode Specera claims to fix, and it is provable from the vendor's own format.
- `FACT` **Requirements are mid-migration and Ultimate-gated.** "requirements and test cases are being migrated to work items", forcing `requirements_v2` where work items are on. `INFERENCE`: a schema in flight is a poor foundation for a customer's compliance programme — and a window for Specera.
- `FACT` **GitLab's AI cannot approve.** Security Review Flow "never sets the **Approve** state, even when it finds no issues"; it sets Request changes for critical/high and Comment otherwise. Duo Code Review's docs never claim approval authority. `INFERENCE`: as with GitHub, the AI produces prose, and the merge record contains no machine-checkable statement that anything was verified.
- `FACT` **Duo Code Review (non-agentic) has a 120-second timeout**; overruns "surface as generic errors", and the automatic retry "omits original file contents, reducing the context the model has when reviewing" (https://docs.gitlab.com/user/gitlab_duo/code_review/). `INFERENCE`: a degraded silent retry means review quality varies with MR size in a way the MR record does not disclose.
- `FACT` **Everything that matters for traceability is Ultimate.** Requirements, external status checks, MR approval policies, compliance center, audit event streaming, report artifacts in release evidence, Security Analyst agent — all Ultimate, whose price is "contact sales" (https://about.gitlab.com/pricing/). `INFERENCE`: GitLab's traceability story is unpriced and unavailable to Premium customers; that is a commercial gap Specera can sit in.
- `FACT` **Billing shifted to metered credits mid-flight.** GitLab Credits introduced 18.7, $1/credit on demand, Premium includes $12/user/mo and Ultimate $24/user/mo as a "limited-time promotion"; consumption rates are per-flow (Code Review Flow 4 executions/credit; SAST False Positive Detection 1/credit; **SAST Vulnerability Resolution 0.25 executions per credit — i.e. 4 credits per run**) (https://docs.gitlab.com/subscriptions/gitlab_credits/). `INFERENCE`: at $1/credit, always-on agentic security resolution is ~$4 per invocation; org-wide always-on AI has no fixed cost ceiling.
- `FACT` **Two overlapping commercial models coexist.** Duo Pro / Duo Enterprise seats "are not billed based on usage and do not consume GitLab Credits", while the Agent Platform is credit-billed; and `FACT` from **2026-05-21 Duo Core users lose non-agentic Chat** on all versions, being pushed to Agent Platform features. `INFERENCE`: customers currently hold SKUs that GitLab is actively deprecating around them — real adoption friction, and a reason buyers may prefer a vendor-neutral evidence layer.
- `FACT` **External agents are outside GitLab's safety controls**: they "lack the same prompt scanning protections as native GitLab agents and depend entirely on third-party provider security controls" (external agents doc). `INFERENCE`: the most capable agents on the platform are the least governed ones — directly contradicting the compliance pitch.
- `FACT` **Beta sprawl in exactly the SDLC rows Specera cares about**: MR Summary (Beta), Code Review Summary (Experiment), Issue Description Generation (Beta), Security Review Flow (Beta, 19.1), Secret False Positive Detection (Beta) (https://docs.gitlab.com/user/gitlab_duo/feature_summary/).
- `UNVERIFIED` **Release evidence immutability.** The docs describe collection and download but say nothing about hashing, signing, or tamper-evidence. Would be verified by a documented digest/signature on the evidence object or an audit event on evidence mutation. Until then, "auditable" means "exportable", not "tamper-evident".
- `UNVERIFIED` **Duo AI data residency.** The data-usage page names Anthropic, Fireworks AI (zero-retention, Codestral), Google Gemini and OpenAI as subprocessors and notes some Anthropic/OpenAI models are "subject to limited vendor-side data retention", but **does not state processing regions**. GitLab Dedicated is single-tenant on AWS with customer-chosen primary/DR/backup regions (https://docs.gitlab.com/administration/dedicated/); whether Duo inference stays in-region is not documented on the fetched pages. Would be verified by a Duo-specific regional-processing page.

## 6. Security, deployment, and license

**License** — `FACT` GitLab Community Edition is under the **MIT (Expat) License**; the `ee/` directory is under the proprietary **GitLab Enterprise Edition license** (https://docs.gitlab.com/development/licensing/). `INFERENCE`: every capability discussed above (Duo, requirements, status checks, approval policies, compliance center) is EE — source-available for inspection but **not reusable**. Nothing here is borrowable code. `UNVERIFIED`: licence of the AI Gateway component — the licensing page does not mention it; would be verified by reading `LICENSE` in the `gitlab-org/modelops/applied-ml/code-suggestions/ai-assist` repo.

**Pricing** — `FACT` Free $0; Premium **$29/user/month billed annually**; Ultimate contact-sales. Add-ons: Enterprise Agile Planning $15/user/mo; compute $10 per 1,000 minutes; storage $5/mo per 10 GiB. AI: **GitLab Credits at $1/credit on demand**, with Premium including $12 and Ultimate $24 per user per month (https://about.gitlab.com/pricing/, https://docs.gitlab.com/subscriptions/gitlab_credits/). Billing is at root-namespace level with a shared Monthly Commitment Pool; unused included credits do not roll over. Duo Pro / Duo Enterprise remain seat-based and credit-exempt.

**Training on customer code** — `FACT` "GitLab does not train generative AI models"; "All GitLab AI model sub-processors are restricted from using model input and output to train models"; zero-retention policy with Fireworks AI; prompt-cache data "never logged to any persistent storage"; chat history retained on GitLab.com for anti-abuse and user-deletable (https://docs.gitlab.com/user/gitlab_duo/data_usage/). `FACT` Caveat in the same doc: some Anthropic and OpenAI models are "subject to limited vendor-side data retention".

**Deployment** — `FACT` Three offerings, and unusually the *entire* Duo feature set including the Agent Platform is available on all three (GitLab.com, Self-Managed, Dedicated) per the feature summary. `FACT` Duo Self-Hosted (Duo Enterprise add-on; "GitLab Duo Agent Platform Self-Hosted" add-on for offline licences) supports vLLM, AWS Bedrock and Azure OpenAI backends and air-gapped operation. `FACT` Dedicated is single-tenant on AWS with customer-selected primary/DR/backup regions.

**Compliance** — `FACT` Dedicated documentation names **SOC 2 and ISO 27001**, deferring detail to GitLab's Trust Center (https://docs.gitlab.com/administration/dedicated/). `UNVERIFIED`: FedRAMP status — `https://about.gitlab.com/security/certifications/` returned **HTTP 404** on 2026-08-04; would be verified from GitLab's Trust Center. `FACT` Compliance tooling (Ultimate): compliance frameworks, compliance center with standards-adherence and violations reporting, audit events, audit reports, and audit event streaming to S3 / GCP Logging.

**Auth / tenancy** — `FACT` External agents run as **service accounts** with credentials supplied as CI/CD variables. `FACT` External status checks authenticate callbacks with an **HMAC shared secret**, and check configuration applies to *new* merge requests only.

**Prompt-injection surface** — `INFERENCE` (rests on documented triggers): agents are triggered by issue creation, work-item status change, MR events, and `@GitLabDuo` mentions — all attacker-writable on public projects — and external agents "execute CI/CD pipelines", i.e. run repo-defined commands under a service account. `FACT` GitLab states external agents lack the prompt-scanning protections native agents have. `INFERENCE`: the highest-privilege, least-protected path on the platform is exactly the popular one (Claude Code / Codex as external agents).

## 7. Ideas to adopt or avoid

### Adopt

- **The `artifacts:reports:` contract, done properly.** GitLab proved that "a CI job emits a report file and the platform ingests it into a first-class object" is the right ingestion shape and that customers will wire it up. Specera should ship the identical ergonomic — a `specera.json` report artifact — but the schema must carry, per requirement: the commit SHA, the test node IDs that exercised it, the assertion outcomes, the scanner run IDs, and a digest. GitLab's schema carries a bare verdict; that delta *is* the product.
- **External status checks as the integration point, not a competing UI.** HMAC-signed callback + "Status checks must succeed" is a documented, GA, merge-blocking seam. Specera should ship a GitLab status-check provider on day one; it is a cleaner gate than GitHub's Checks API and requires no weakening of protections.
- **Release evidence as the unit of delivery.** A JSON object collected at release time, containing the release, its milestones, and the pipeline's report artifacts, downloadable for external audit, is the right *shape* for Specera's output. Specera should produce the same object with the pieces GitLab omits: content-addressed digests, a signature, and per-requirement evidence chains.
- **in-toto / SLSA provenance for the evidence itself.** GitLab already emits in-toto v0.1 statements with SLSA 1.0 predicates for build artifacts. Specera should emit its traceability evidence as an in-toto attestation over the same predicate machinery rather than inventing a format — it makes the evidence verifiable by tooling customers already run, and answers "is this tamper-evident" with a signature instead of a claim.
- **Policy-as-code in a separate, protected project.** MR approval policies live in a dedicated security-policy project with group-level enforcement, `enforcement_type: warn` for staged rollout, and audit events on bypass. Specera's traceability rules should be versioned the same way — including the warn mode and the bypass audit event, which is what makes the control credible to an auditor.
- **`CI_HAS_OPEN_REQUIREMENTS`-style gating variables.** Exposing "is there anything to verify" as a CI variable lets customers skip cost when there is nothing to check. Cheap, and directly applicable to metered agent runs.

### Avoid

- **A wildcard that satisfies everything.** `{"*":"passed"}` marking all open requirements satisfied makes the whole mechanism ceremonial. Specera must require per-requirement evidence and reject blanket assertions outright.
- **AI that cannot approve *and* cannot block.** GitLab's flows set Comment or Request changes and never Approve. Advisory-only output produces no record. Specera's output must be a status check with a stable identifier and a signed payload.
- **Migrating the compliance object mid-life.** Requirements → work items with a `requirements`/`requirements_v2` CI key split is a breaking change to the exact artifact customers put in audit binders. Specera should version its report schema explicitly and never rename a key in a compliance path.
- **Gating traceability behind the contact-sales tier.** Requirements, status checks, approval policies and audit streaming are all Ultimate. `INFERENCE`: this is why the capability exists but is under-adopted — and it is Specera's opening.
- **Two live billing models at once.** Seat-based Duo Pro/Enterprise alongside credit-metered Agent Platform, with Duo Core losing Chat on 2026-05-21, is procurement chaos.
- **Ungoverned third-party agents.** Shipping external agents without the prompt-scanning applied to first-party agents inverts the security story. Specera should apply *identical* input handling to every agent it hosts, first- or third-party.

## 8. Build, borrow, buy, integrate, or reject

**Integrate — and treat as the benchmark, not the also-ran.** Borrowing is impossible: everything relevant is under the proprietary GitLab EE licence in `ee/`, not the MIT CE tree, so there is no code to reuse and no licence path to reuse it. Integration is unusually clean, though: external status checks (HMAC, merge-blocking, GA, Ultimate) plus `artifacts:reports:` ingestion plus the release-evidence API give Specera a supported way to be the evidence layer *inside* GitLab rather than a competing pane. `INFERENCE`: the strategic finding is uncomfortable and should be stated plainly to the sponsor — for a GitLab Ultimate customer, Specera's proposed scope is roughly 70% redundant today, and the defensible 30% is the *quality* of the evidence (per-requirement chains, digests, signatures, tamper-evidence) and the cross-vendor case (Jira + GitHub, which GitLab by definition does not serve). If Specera's thesis is "one system should own the chain", GitLab already won that argument; Specera's thesis has to be "the chain must be *provable*, across systems you do not control."
